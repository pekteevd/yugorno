# Журнал разработки Югорно

## Текущий этап: API публикаций и серверный профиль

### Основа и визуальный слой
- Сохранён HTML/CSS-прототип с семью исходными разделами.
- Восстановлены семь исходных фото-адресов из утверждённого прототипа в CSS-переменных и `public/assets/images.json`.
- Замену фотографий можно будет делать через `public/assets/images/` и каталог `images.json`, без правки HTML.
- Локальные фотографии пока не включены: исходный прототип использовал внешние Unsplash-адреса. Если внешняя сеть недоступна в Telegram WebView, сами изображения могут не загрузиться. На этом этапе не подменяем их новыми макетами.

### Сервер
- Добавлен `data-store.js`: хранение путешествий, сообществ и профилей в JSON вне `public/`.
- Записи сериализованы через очередь и сохраняются атомарной заменой файла.
- Добавлены API: `GET/POST /api/trips`, `GET/POST /api/communities`, `GET/PUT /api/profile`, `POST /api/trips/:id/interest`, `POST /api/communities/:id/join`.
- Отклики на путешествия и участники сообществ сохраняются без дублей.
- Публичные кнопки «Откликнуться» и «Присоединиться» подключены к защищённым API.
- Публичные списки не раскрывают Telegram ID авторов.
- Добавлен список собственных публикаций и просмотр откликов только владельцем путешествия.
- В списке откликов показываются только добровольно заполненные поля профиля участника.
- При новом отклике или вступлении отправляется попытка Telegram-уведомления владельцу публикации; ошибка доставки не отменяет сохранённое действие.
- Изменяющие запросы и личный профиль требуют проверенную Telegram `initData`.
- Для ранней версии используется JSON-хранилище одного процесса. Для масштабирования потребуется внешняя БД и постоянный диск хостинга.

### Клиент
- Формы путешествия и сообщества отправляют данные в API, а не только в оперативный массив.
- После Telegram-аутентификации загружаются опубликованные записи и серверный профиль.
- Вне Telegram профиль остаётся только локальным черновиком; публикация заблокирована.
- Вывод пользовательского текста в карточках экранируется.
- Telegram viewport обновляется при `viewportChanged`.

### Безопасность
- Авторизация отклоняет повторяющиеся параметры `initData`.
- Сортировка полей HMAC не зависит от локали сервера.
- Telegram user ID должен быть положительным безопасным целым числом.
- Серверный `/api/auth/telegram` не считает сессию успешной без подтверждённого user ID.

### Проверки
- `npm test`: 15 тестов пройдены.
- `node --check`: серверный модуль, модуль хранилища, Telegram auth и inline JavaScript проверены.
- Проверка браузерного скриншота Chromium в этой среде заблокирована политикой среды (`ERR_BLOCKED_BY_ADMINISTRATOR` для локального HTTP); визуальный мобильный тест не отмечен как пройденный.
- Express-зависимость не установлена в рабочей среде, поэтому полный HTTP integration test сервера здесь пока не выполнен.

### Следующие задачи после этапа 0.4
1. Проверить запуск Express и все API-маршруты в среде с установленными зависимостями.
2. Проверить сохранность `data/` на постоянном диске Deployka до production-развёртывания.
3. Улучшить сценарий связи организатора с откликнувшимися, не раскрывая Telegram ID.
4. После согласования пользователя заменить исходные фото выбранными локальными файлами.
5. Подключить интерактивную карту и личные сообщения отдельными этапами.

Production Deployka и GitHub не изменялись.

- Серверные методы проверяют владельца записи перед изменением или просмотром списка участников.
- Добавлены тесты владения, редактирования, снятия публикаций, приватности участников.

## 2026-11-19 — этап 0.5: управление участниками

- Каждое вступление получает отдельный случайный ID членства; он не является Telegram ID. Старые записи автоматически получают такой ID при первом просмотре списка владельцем.
- Владелец сообщества может убрать участника из сообщества.
- Удаление участника проверяет владельца сообщества на сервере; Telegram ID участника не передаётся в клиентский список.
- Добавлены тесты на удаление участника, запрет чужому владельцу и отсутствие userId в публичной модели участника.
- Визуальный рендер и HTTP-интеграция всё ещё ожидают среды с доступным Express и браузерным тестированием.


## 2026-11-19 — этап 0.5.1: безопасный локальный запуск

- Добавлена переменная `DISABLE_BOT_POLLING=true`: локальная копия с настоящим BOT_TOKEN может проверять Telegram initData и отправлять Bot API-уведомления, но не запускает `getUpdates`.
- Это исключает конфликт Long Polling с действующим ботом на Deployka при локальном тестировании.
- Статус `/api/status` теперь отдельно показывает, включён ли polling.
- Версия проекта повышена до 0.5.1.

## 2026-11-26 — второй этап карты: фотографии, защита от дублей, модерация и GPX

- В форме впечатления добавлена фотография JPEG/PNG/WebP. Перед отправкой браузер уменьшает изображение и повторно кодирует его в JPEG, удаляя EXIF-метаданные; сервер проверяет сигнатуру содержимого и ограничивает размер файла.
- Добавлена серверная защита от повторной публикации места с тем же названием и категорией в радиусе 75 метров. Проверка не объединяет и не удаляет существующие записи; при совпадении возвращается конфликт с карточкой совпадения.
- В интерфейсе модератора появилась очередь мест, впечатлений и маршрутов с действиями «Опубликовать» и «Отклонить». Кнопка показывается только аккаунтам, прошедшим серверную проверку роли.
- Добавлен импорт GPX (до 5000 точек) в форму маршрута, сохранение проверенных координат трека, отображение трека на карте и экспорт маршрута обратно в GPX. Если GPS-трека нет, экспорт использует координаты остановок и не выдаёт их за реальную дорогу.
- Добавлены тесты на обнаружение дублей, валидацию и сохранение GPS-трека.
- Проверка CI и визуальная проверка в Telegram WebView должны быть выполнены после публикации коммита.
